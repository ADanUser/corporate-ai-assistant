# RUNBOOK — что делать при инциденте

Инструкция для дежурного. Не описание проекта — для этого есть
[README](README.md). Здесь только порядок действий.

**Общее правило: сначала остановить, потом разбираться.**

```
Стоп → Диагноз → Починка → Проверка → Возврат
```

Диагностика занимает минуты, а ассистент всё это время продолжает
обрабатывать запросы. Выключить инструмент стоит одну команду и
обратимо; невыполненное действие пользователь сделает руками, как делал
до внедрения. Необратимое действие обратно не вернёшь.

Не всякая жалоба требует рубильника:

| Тип проблемы | Первое действие |
|---|---|
| Нарушен контроль безопасности (действие без approval, чужой документ в ответе, самоподтверждение прошло) | **Выключить инструмент немедленно**, даже по одному сообщению |
| Деградация качества (невнятный ответ, найден не тот документ) | Сначала посмотреть журнал, выключать не нужно |

Разница в обратимости. Плохой ответ пользователь прочитал и забыл.
Созданная задача осталась в трекере.

## Инцидент 1. Действие выполнено без подтверждения

**Признак:** пользователь сообщает, что задача создана, хотя он её не
подтверждал. Или в журнале есть `tool_executed` для `create_task`.

Самый серьёзный класс инцидентов: обойдён human-in-the-loop.

### 1. Остановить

```bash
curl -X POST localhost:8000/admin/tools \
  -H "Content-Type: application/json" \
  -d '{"username": "admin", "action_name": "create_task", "enabled": false}'
```

Ответ содержит `disabled_actions` — убедись, что инструмент в списке.
После этого `create_task` недоступен всем, включая Admin.

### 2. Найти событие в журнале

```bash
curl -s localhost:8000/audit | python -m json.tool | grep -B2 -A8 "task_approved"
```

Смотри на три поля:

| Поле | Что означает |
|---|---|
| `approver` | кто подтвердил. `null` или отсутствует — approval не было |
| `user_id` | кто запросил |
| `thread_id` | по нему собирается вся цепочка события |

Полная траектория одного запроса:

```bash
curl -s localhost:8000/audit | python -c "
import json,sys
tid = 'task-XXXXXXXX'
for e in json.load(sys.stdin)['events']:
    if e.get('thread_id') == tid:
        print(e['timestamp'], e['event_type'], e['details'])
"
```

### 3. Определить причину

| Что видно в журнале | Причина | Что делать |
|---|---|---|
| `tool_executed`, `approver` отсутствует | инструмент помечен низким риском | проверить `risk_level` в `app/tools.py` |
| `task_approved`, `approver` == `user_id` | не сработал запрет самоподтверждения | проверить `/approve` в `app/main.py` |
| `task_approved`, `approver` — другой человек | **инцидента нет** | задачу подтвердил коллега; сообщить пользователю |
| `tool_selected` с чужим инструментом | маршрутизатор выбрал не то | не инцидент безопасности, см. Инцидент 4 |

Третья строка — самый частый исход. Прежде чем чинить код, убедись, что
поломка вообще была.

### 4. Починить и проверить

Типовая причина — неверный `risk_level` в карточке инструмента.
Approval выводится из уровня риска:

```python
APPROVAL_REQUIRED_LEVELS = {"high", "critical"}
```

Инструмент, который пишет во внешнюю систему, обязан иметь `high` или
`critical`. После правки — **обязательно полный прогон**:

```bash
python -m evals.runner
```

Метрика `approval_compliance` должна быть 100%. Быстрых тестов
(`pytest -q`) здесь недостаточно: они проверят карточку, но не проверят,
что задача действительно не создаётся без approval.

### 5. Вернуть инструмент

```bash
curl -X POST localhost:8000/admin/tools \
  -H "Content-Type: application/json" \
  -d '{"username": "admin", "action_name": "create_task", "enabled": true}'
```

Только после зелёного прогона. Не по памяти о том, что «раньше работало».

## Инцидент 2. В ответе оказался недоступный документ

**Признак:** сотрудник получил данные, которых его роль видеть не должна
(зарплатные вилки, премии).

Утечка по правам. Останавливать инструментом нечего — фильтр работает в
ветке вопросов, а не в ветке действий.

### 1. Оценить масштаб

```bash
curl -s localhost:8000/audit | python -m json.tool | grep -A5 "answer_generated"
```

Поле `source` показывает, из какого документа собран ответ. Ищи
`Finance Confidential` в ответах пользователей с ролью Employee или
Manager.

### 2. Проверить фильтр

Фильтр применяется **до** поиска, в `permission_node`:

```python
allowed = filter_documents_by_role(DOCUMENTS, role)
```

Быстрая проверка без сервера:

```bash
python -c "
from app.data.documents import DOCUMENTS
from app.permissions import filter_documents_by_role
for role in ('Employee','Manager','Admin'):
    print(role, [d['id'] for d in filter_documents_by_role(DOCUMENTS, role)])
"
```

`salary_bands` и `bonus_policy` должны быть только у Admin.

### 3. Проверить метаданные документа

Частая причина — не баг в фильтре, а неверный `allowed_roles` в самом
документе (`app/data/documents.py`). Новый документ добавили и
скопировали список ролей от соседнего.

### 4. Проверить после починки

```bash
pytest -q                    # мгновенно, поймает поломку фильтра
python -m evals.runner       # метрика permission_safety обязана быть 100%
```

**Если утечка подтвердилась** — сообщить владельцу документа и
безопаснику: люди увидели данные, которых видеть не должны. Технической
починки здесь недостаточно.

## Инцидент 3. Модель недоступна

**Признак:** в журнале много событий `intent_llm_error`,
`answer_llm_error`, `tool_router_llm_error`. Ассистент отвечает сырым
текстом документов вместо связных ответов.

Это **не авария**, а деградация. Система спроектирована на такой случай.

### Что продолжает работать без модели

| Слой | Работает? |
|---|---|
| Детектор prompt injection | да — список подстрок, без LLM |
| Фильтр документов по роли | да — чистый Python |
| Реестр инструментов, права, kill switch | да |
| Separation of duties | да |
| Классификация намерения | нет → откат в безопасное `question` |
| Генерация ответа | нет → сырой текст документа |
| Семантический поиск | нет — эмбеддинги тоже идут через API |

Безопасность не деградирует. Деградирует удобство.

### 1. Найти причину

```bash
curl -s localhost:8000/audit | python -m json.tool | grep -A3 "llm_error"
```

Поле `error` содержит текст от провайдера:

| В тексте ошибки | Причина | Что делать |
|---|---|---|
| `429`, `RESOURCE_EXHAUSTED` | исчерпана квота | ждать сброса или поднять лимит |
| `401`, `API key not valid` | ключ протух | обновить `GEMINI_API_KEY` в `.env`, перезапустить |
| `503`, `UNAVAILABLE` | у провайдера сбой | ждать, ретраи отработают сами |
| `404`, `model not found` | имя модели изменилось | поправить `_MODEL` в `app/llm.py` |

Ретраи (2 → 4 → 8 секунд) уже встроены в `generate_text()` — короткие
всплески система переживает сама. Записи в журнале появляются только
после исчерпания четырёх попыток.

### 2. Решить, оставлять ли сервис включённым

Ассистент в деградированном режиме отвечает хуже, но безопасно. Если
жалоб на качество много — предупредить пользователей, а не выключать:
режим «сырой текст документа» полезнее, чем недоступный сервис.

## Инцидент 4. Ассистент отвечает не по делу

**Признак:** ответы невнятные, находится не тот документ, вопрос уходит в
инструмент вместо поиска.

Проблема качества. Рубильник не нужен, разбираемся спокойно.

### Куда смотреть

| Симптом | Событие в журнале | Где искать причину |
|---|---|---|
| Вопрос ушёл в действие | `tool_selected` вместо `answer_generated` | `INTENT_PROMPT` в `app/nodes.py` |
| Выбран не тот инструмент | `tool_selected` с чужим именем | `description` карточки в `app/tools.py` |
| «Не найдено» на существующее правило | `no_source_answer` | `RELEVANCE_THRESHOLD` в `app/search.py` |
| Ответ не по документу | `answer_generated` | `ANSWER_PROMPT` в `app/nodes.py` |

### Прежде чем чинить — воспроизвести

Классификатор намерения недетерминирован: одна и та же формулировка
между прогонами может уйти в разные ветки. Прогони запрос три-четыре раза:

```bash
python -c "
from app.llm import generate_text
from app.nodes import INTENT_PROMPT
q = 'сюда формулировку пользователя'
for _ in range(4):
    print(repr(generate_text(INTENT_PROMPT.format(question=q))))
"
```

Если результат плавает — это разброс модели, а не баг. Чинится
уточнением промпта или новым few-shot примером, но гарантий нет.

### После правки промпта

**Обязателен полный прогон.** Промпт — не локальная правка: одно
уточнение чинит один кейс и ломает три соседних.

```bash
python -m evals.runner
```

Если `task_success` упал ниже 85% — правку откатить, а не «дожимать».

## Откат

### Откатить правку промпта или карточки

```bash
git log --oneline -10
git revert <хеш>
```

`revert`, а не `reset`: история остаётся, откат виден в ней явно.

### Откатить релиз целиком

```bash
git revert <хеш> && git push
```

CI прогонит быстрые тесты автоматически. Полный прогон eval — вручную,
до объявления инцидента закрытым.

### Что откатом не чинится

| Состояние | Почему | Что делать |
|---|---|---|
| Незавершённые approval-паузы | `InMemorySaver`, живут в памяти процесса | при перезапуске теряются; попросить пользователей повторить запрос |
| Отключённые инструменты | множество в памяти | после рестарта включаются обратно **сами** — проверить `/admin/tools` |
| Счётчики лимитов | в памяти | обнуляются при рестарте |

Последняя строка первой таблицы — ловушка: аварийно выключенный
инструмент после перезапуска сервиса молча возвращается в строй.
**После каждого рестарта во время инцидента проверяй kill switch заново.**

## Владелец и границы

| Что | Кто |
|---|---|
| Владелец сервиса | автор проекта |
| Kill switch, доступ к журналу | роль Admin |
| Право подтверждать действия | роли Manager, Admin |
| Изменение прав на документы | владелец документа |

**Что дежурный делает сам:** kill switch, чтение журнала, откат правки,
перезапуск сервиса.

**Что не делает без владельца:** меняет `allowed_roles` документов,
добавляет инструменты, повышает лимиты, снимает approval с рискованного
действия.

## Добавление нового инструмента

Инструмент — это новая возможность что-то сделать во внешнем мире,
поэтому проходит через проверку, а не добавляется на ходу.

1. Карточка в `TOOL_REGISTRY` (`app/tools.py`). Все поля обязательные —
   забыть риск или роли не получится, приложение упадёт при старте.
2. `risk_level` честно: пишет во внешнюю систему → `high` или `critical`.
   Это единственный способ обойти approval, поэтому единственное место,
   где можно навредить осознанно.
3. Функция исполнения + ветка в `execute_tool` (`app/nodes.py`).
4. Eval-кейсы в `evals/cases.py`: минимум один happy path и один отказ.
5. `pytest -q` и `python -m evals.runner` — обе блокирующие метрики 100%.

Инструмент без eval-кейсов в реестр не добавляется. Иначе первый раз его
поведение проверит пользователь.

## Ограничения этого runbook

- **Прода нет.** Все команды приведены для локального запуска
  (`localhost:8000`). Пилота на реальной команде не проводилось; это
  план реагирования, а не отчёт об инцидентах.
- **Журнал доступен всем.** Эндпоинт `/audit` не требует авторизации —
  в проде он должен быть закрыт ролью Admin.
- **Алертов нет.** Инцидент обнаруживается по жалобе пользователя, а не
  по метрике. Нужен мониторинг доли `answer_type` в отказах и частоты
  событий `*_llm_error`.
- **Состояние в памяти.** Kill switch, лимиты и паузы не переживают
  рестарт и не разделяются между воркерами `uvicorn --workers N`.
  В проде — Redis и БД.
